# Age L1 — la blockchain de Age of Avax

Age of Avax corre sobre su propia **L1 de Avalanche** (antes "subnet"), con máquina virtual **Subnet-EVM**. Tener cadena propia permite bloques de ~1 s, gas casi nulo para el jugador y control total sobre la emisión del token de gas.

## Parámetros

| Parámetro | Valor |
|---|---|
| Nombre | `ageL1` |
| VM | Subnet-EVM (compatible con EVM, contratos en Solidity) |
| Chain ID | `777010` |
| Token de gas | **AGE** (18 decimales) |
| Tiempo objetivo de bloque | 1 s (`targetBlockRate: 1`) |
| Límite de gas por bloque | 15.000.000 |
| Gas objetivo por ventana | 60.000.000 |
| Base fee mínimo | 1 gwei (`minBaseFee: 1000000000`) |
| Denominador de cambio de base fee | 36 |
| Costo de bloque | 0 → 1.000.000, paso 200.000 |
| Hardforks EVM | todos activos desde el bloque 0 (hasta London) |
| Contratos | compilados con `solc 0.8.28`, `evm_version = cancun` |

### Precompilados activos

| Precompilado | Para qué sirve | Admin |
|---|---|---|
| **Warp** (`warpConfig`) | Mensajería entre cadenas de Avalanche (ICM/Teleporter). Quórum 67%, exige firmas de la red primaria. | — |
| **FeeManager** (`feeManagerConfig`) | Cambiar la configuración de comisiones sin hard fork. | `0x8db97C7cEcE249c2b98bDC0226Cc4C2A57BF52FC` |
| **NativeMinter** (`contractNativeMinterConfig`) | Acuñar AGE nativo (faucet, recompensas de gas). | `0x8db97C7cEcE249c2b98bDC0226Cc4C2A57BF52FC` |

### Asignación inicial (génesis)

| Cuenta | AGE |
|---|---|
| `0x8db97C7cEcE249c2b98bDC0226Cc4C2A57BF52FC` (deployer / admin) | 1.000.000 |
| `0x3a44…8e82` | 600 |

> ⚠️ `0x8db9…52FC` es la cuenta **"ewoq"**, la clave de pruebas pública de Avalanche. Sirve solo para la red local. Antes de cualquier testnet o mainnet hay que generar un génesis nuevo con admins propios (idealmente un multisig).

El génesis completo está en `chain/genesis.json`.

## Levantar la L1 en local

Requisitos: [avalanche-cli](https://docs.avax.network/tooling/avalanche-cli).

```bash
# crear (solo la primera vez) con el génesis del repo
avalanche blockchain create ageL1 --evm --genesis chain/genesis.json
avalanche blockchain deploy ageL1 --local

# en sesiones posteriores
avalanche network start
avalanche blockchain describe ageL1     # muestra el RPC y el chain ID
```

El RPC local tiene esta forma:

```
http://127.0.0.1:9660/ext/bc/<blockchainID>/rpc
```

Guárdalo en `chain/.env` (no se versiona):

```bash
AGE_RPC_URL=http://127.0.0.1:9660/ext/bc/<blockchainID>/rpc
AGE_CHAIN_ID=777010
DEPLOYER_PK=0x...      # clave del deployer (en local: ewoq)
REPORTER_PK=0x...      # clave del verificador de partidas
REPORTER=0x...         # dirección del verificador
VITE_AGE_RPC_URL=$AGE_RPC_URL
VITE_AGE_CHAIN_ID=777010
```

Y en `game/.env.local` solo las variables `VITE_*`.

## Age L1 en Fuji (testnet pública)

Despliegue con el validador corriendo en esta Mac. Las claves viven en el almacén de avalanche-cli y nunca se imprimen.

| Parámetro | Valor |
|---|---|
| Nombre en avalanche-cli | `ageFuji` |
| Chain ID | **777011** (la red local usa 777010) |
| Validación | Proof of Authority, 1 validador inicial |
| Dueño del Validator Manager y de su proxy | `0x168f4f058d02528d112Bf7934FAEfC021637499D` (`ageDeployer`) |
| Admin de NativeMinter y FeeManager | `ageDeployer` |
| Asignación inicial | 1.000.000 AGE a `ageDeployer` (sin la clave pública de pruebas) |
| Verificador / relayer | `0x7ef4259D8cd2966c9FB4fcF015895b34ea999099` (`ageReporter`) |
| Génesis | `chain/genesis.fuji.json` |

```bash
chain/fuji.sh fondos      # saldos (basta con 0,5 AVAX de Fuji en la C-Chain de ageDeployer)
chain/fuji.sh p-chain     # pasa 0,45 AVAX a la P-Chain
chain/fuji.sh saldo       # saldo del validador · chain/fuji.sh recargar 0.5 para sumarle
chain/fuji.sh desplegar   # crea la L1 y arranca el validador local (sincroniza la P-Chain de Fuji)
chain/fuji.sh contratos   # despliega los contratos y escribe chain/.env.fuji
./publicar.sh             # servidor + Tailscale Funnel (URL fija) + sitio de Vercel apuntando al servidor
```

AVAX de Fuji: https://core.app/tools/testnet-faucet/ (con un cupón de Team1 dan más).

**¿Cuánto AVAX hace falta?** Crear la L1 cuesta centésimas de AVAX. Lo que sí consume es la **cuota continua del validador** (ACP-77), ~1,33 AVAX al mes, que se descuenta de su saldo en la P-Chain. Con 0,5 AVAX se deja un saldo de 0,3, que alcanza para ~1 semana. Si el saldo llega a cero, el validador se desactiva y la L1 deja de producir bloques, pero no se pierde nada: se reactiva al recargarlo con `chain/fuji.sh recargar`.

### Publicación (Tailscale Funnel)

El sitio vive en **https://ageofavax.app** (dominio comprado en Vercel, que redirige a `www.ageofavax.app`; la dirección anterior `age-of-avax.vercel.app` sigue funcionando).

`publicar.sh` levanta el servidor del juego contra la L1 de Fuji y lo publica con **Tailscale Funnel**, que da una URL `https://<equipo>.ts.net` fija (antes se usaba un túnel rápido de Cloudflare, que cambiaba de URL y se borraba en minutos). El sitio de Vercel apunta a esa URL con `VITE_API_URL`; como no cambia, Vercel solo se reconstruye la primera vez o al cambiar de equipo. El servidor también hace de proxy del RPC (`/rpc`), así que el nodo no se expone directamente.

**Mudar el nodo y el servidor a una PC con Linux** (para que no dependan de la laptop):

```bash
bash migrar/empaquetar.sh               # en la Mac: apaga todo y empaqueta nodo, llaves y servidor (bash migrar/empaquetar.sh cancelar lo revierte)
bash migrar/instalar-linux.sh paquete.tgz   # en la PC: avalanchego + subnet-evm para Linux, servicios systemd age-nodo y age-servidor, Funnel
```

En Linux, `systemd` arranca el nodo y el servidor al prender la PC y los reinicia si se caen (reemplaza a `vigilante.sh`). El paquete lleva las llaves del validador y del verificador: no se sube a la nube y se borra al terminar. **Nunca corras el nodo en los dos equipos a la vez**, porque comparten llaves.

El instalador pide la contraseña de `sudo` una vez y la mantiene vigente hasta el final. Si se corta a medias, no se vuelve a correr completo, porque se niega a sobrescribir el nodo ya restaurado: se repiten solo los pasos que faltan.

El plugin de la L1 tiene que ser el **subnet-evm de la misma versión que avalanchego**. Desde v0.8.0, subnet-evm sale dentro de los releases de avalanchego (`subnet-evm-linux-amd64-v1.15.1.tar.gz`). El v0.8.0 de su repo viejo, que es el que anota `sidecar.json`, habla el protocolo RPCChainVM 44 y avalanchego 1.15.1 exige el 46. Si no coinciden, el log del nodo dice `failed to register VM … protocol version mismatch` y la L1 no arranca, aunque la P-Chain sincronice.

**Actualizar el servidor cuando cambian las reglas.** La página se publica sola en Vercel con cada push, pero el servidor de la PC usa su propia copia del código para re-simular cada partida antes de pagar GLORY. Si cambia `SIM_VERSION` (mapas, recursos, costos, combate…), justo después de que Vercel publique hay que correr en la PC:

```bash
cd ~/age10 && git pull && sudo systemctl restart age-servidor
```

`/api/health` (por ejemplo `https://desktop-j7thev3.tail736af2.ts.net/api/health`) muestra la versión del servidor en `simVersion`, que debe coincidir con la de la página. Mientras no coincidan, el verificador rechaza las victorias con "versión de reglas distinta". Los cambios que solo tocan la interfaz, el render o la documentación no necesitan este paso.

**En Windows con WSL2** (la mudanza actual: Ubuntu en WSL con `systemd=true` en `/etc/wsl.conf`):

- **WSL se apaga cuando no hay ninguna terminal abierta**, y con eso se caen el nodo y el servidor. Hace falta una tarea programada de Windows que lo mantenga vivo al iniciar sesión (`wsl.exe -d Ubuntu --exec /bin/sleep infinity`). También hay que quitar la suspensión de Windows con `powercfg`, porque bloquearla dentro de Ubuntu no detiene a Windows.
- **La red de WSL puede ser mucho más lenta que la de Windows.** Con la tarjeta Wi-Fi USB de esta PC medimos unos 80 KB/s por conexión contra ~1 MB/s en Windows, con muchas retransmisiones TCP. A esa velocidad, las respuestas de bootstrap (hasta 2 MB) no llegan en los 10 s que espera el nodo, y la P-Chain se queda en `starting to fetch blocks` sin avanzar. Se arregló subiendo los tiempos de espera en el `flags.json` del nodo y reiniciándolo:
  ```json
  "network-initial-timeout": "30s",
  "network-maximum-timeout": "90s",
  "bootstrap-max-time-get-ancestors": "200ms"
  ```
  Apagar los offloads de `eth0` con `ethtool` (servicio `wsl-offloads`) no cambió la velocidad.
- Funnel corre con el Tailscale de dentro de WSL, así que la URL pública es la de esa máquina (`https://desktop-j7thev3.<tailnet>.ts.net`), y Vercel se reconstruye con ella.

## Camino a producción

1. **Validadores fuera de la laptop:** el validador y el servidor ya pueden vivir en una PC con Linux (`migrar/`); el siguiente paso es un VPS o la nube, y sumar más validadores (PoA → PoS cuando haya comunidad).
2. **Validadores:** con ACP-77 (Avalanche9000) la L1 paga una cuota continua por validador en lugar de stakear 2.000 AVAX en la red primaria.
3. **Puente:** usar Warp/ICM (Teleporter) para mover GLORY o AVAX desde la C-Chain.
4. **RPC público:** exponer el nodo detrás de un proxy con límites de tasa, o usar un proveedor de infraestructura.
5. **Llaves:** el verificador (`REPORTER`) y el admin deben vivir en un KMS o HSM, nunca en `.env`.
